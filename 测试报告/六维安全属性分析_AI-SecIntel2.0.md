# AI-SecIntel 2.0 · 六维安全/质量属性分析

> 分析对象：AI-SecIntel 2.0 漏洞情报分析平台（采集 NVD/KEV/arxiv/GitHub 等源、富化、
> QA/LLM 问答、日报与导出、前端看板）。
> 分析视角：机密性 / 完整性 / 可用性 / 真实性 / 可问责性 / 可靠性（CIA + A² + R）。
> 依据：源码核查（core/server.py, engine.py, daily_digest.py, credibility.py,
> atlas.py, augment.py）+ 本轮交付验证与 CI 归因事实。

---

## 0. 总览评分

| 维度 | 评级 | 一句话结论 |
|------|------|-----------|
| 机密性 Confidentiality | B | 仅本地 127.0.0.1 暴露，但无鉴权、无传输加密、明文落盘 |
| 完整性 Integrity | B+ | 源去重+规范化+canonical URL 降低脏数据，但无密码学完整性校验 |
| 可用性 Availability | B- | 熔断器周到，但单点本地服务、模块停产无自愈、需人工重启 |
| 真实性 Authenticity | B | 溯源字段完备（源/作者/URL），但未对上游数据源做签名验证 |
| 可问责性 Accountability | C+ | 系统级溯源（actor/时间）到位，但无用户身份（无鉴权）导致不可归人 |
| 可靠性 Reliability | B- | 熔断与降级良好，但负载敏感假失败、语料实时漂移带来非确定性 |

---

## 1. 机密性（Confidentiality）

**现状**
- 主服务 `ThreadingHTTPServer(("127.0.0.1", port), ...)` 仅监听本机回环，
  网络侧不可达（`core/server.py:1475`）。
- **无任何认证层**：源码中无 login / password / session / token 校验
  （grep 命中均为分词/文档/CWE 术语，非鉴权实现）。
- 密钥以 `secrets.env`（gitignore）与 `AISEC_LLM_API_KEY` 环境变量管理，
  不入库；调用 LLM 走 HTTPS 出站。
- 所有情报数据、语料、通知均为**明文 JSON 落盘**（`data/corpus.json` 等），无加密。

**风险**
- 本地无鉴权 → 同机任意用户/进程可读全部情报与密钥引用，且浏览器任何人访问
  `127.0.0.1:8848` 即可操作（含导出）。
- 明文落盘 → 设备丢失/备份泄露即全量暴露。
- 无 TLS → 若未来放开绑定到非回环地址，流量明文。

**建议**：本机单机场景风险可控；若需多用户或跨机，必须叠加
反向代理鉴权（Basic/OIDC）+ TLS，并对密钥与导出文件加密。

## 2. 完整性（Integrity）

**现状（正向）**
- **源去重**：日报先按源去重再累加（`daily_digest.py:465-498`），避免重复扫描放大主机数。
- **标题归一去重**：corpus 用标题 Jaccard 归一（`engine.py:2422-2462`），防重复入库。
- **canonical URL 确定性映射**：`engine.py:466-498` 按 CVE/GHSA/安全客/先知等前缀生成稳定原网址。
- **缓存键防伪**：语料缓存键含 `(INDEX_CACHE_VERSION, mtime_ns, size, len(docs), idseq)`，
  源文件变动即失效重建。

**风险**
- **无密码学完整性校验**：JSON 文件无签名/哈希，运维误改或磁盘损坏无法检测。
- **实时漂移致非一致**：用户 8848 持续抓取使语料日增（今日 +10 CVE），
  cmdb 匹配数 203→206，同一查询不同时间结果不同（非篡改，是时效漂移）。
- **源与实时 API 不一致**：3 条 CVE 的归档 CVSS 与 NVD 实时 API 不同（见 CI `_test_cvss_primary`），
  属数据时效性，非完整性破坏，但影响结论可复现。

**建议**：对 `corpus.json`/`dispositions.json` 增加写入时 SHA-256 + 版本号；
关键结论（日报 CVSS 汇总）附数据快照时间戳以便复算。

## 3. 可用性（Availability）

**现状（正向）**
- **熔断器成熟**：`circuit.py` FAIL=3/COOLDOWN=300s，连续失败源（NVD 已 118h 无数据）
  被隔离，避免上游拖死主流程；`dispositions.json` 记录 `auto:circuit` 便于溯源。
- **空结果不等于源挂**：`"持续空>180s"` 才升级，防误判。

**风险**
- **单点本地服务**：仅一个 8848 进程，崩溃/未重启即全平台不可用；
  且**改动 Python 侧后必须人工双击 `启动服务.bat` 重启**，AI 会话内起的服务结束即回收。
- **模块停产无自愈**：`m1_monitor` 台账 10-07 起停产，10-08 起 `_test_daily_digest` 必败，
  直到测试失败才暴露（缺乏存活探活/告警）。
- **前端可用性事故**：火狐 1100~1200px 区间 JS/CSS 断点不一致导致详情页整屏压暗、
  无法关闭（本轮已修复，断点统一为 ≤1200 并补 `z-index:100`）。
- **负载敏感假失败**：CI 批处理并发下 `_test_portability`（探测<1.5s）、
  `_test_qa_round1`（首问<8s）假失败，安静环境单跑即过——影响 CI 可用性信号可信度。

**建议**：加进程守护（重启钩子/看门狗）；为各数据源设"停产/不出数"阈值告警；
CI 计时断言改为相对阈值或单跑隔离。

## 4. 真实性（Authenticity）

**现状（正向）**
- 平台本身将 `CWE-345 Insufficient Verification of Data Authenticity`
  纳入威胁知识库（`augment.py:103`），说明对真实性有方法论自觉。
- 每条记录保留**来源溯源**：源标识（nvd/kev/arxiv/github）、作者
  （`rec["author"]`）、原网址（canonical URL）、在野利用标记（KEV）、
  PoC/补丁信号（`credibility.py` 的 exploit_signals）。
- 富化用 CVE 编号锚定，避免以标题模糊关联。

**风险**
- **未对上游数据源做真实性校验**：NVD/KEV/arxiv 拉取后直接入库，未见
  签名/校验和/发布方证书验证；若某源被投毒或被中间人篡改，平台无法识别。
- **富化链依赖外部链接解析**：`_ver_from_links` 取版本号，错误链接可能引入伪版本。

**建议**：对关键源（NVD JSON Feed）增加发布方签名/ETag 校验；
对"在野利用"等高危判据强制要求多方源交叉确认（已在 m0_ops 多路闸门部分落实）。

## 5. 可问责性（Accountability）

**现状（正向）**
- **系统级溯源完备**：`dispositions.json` 记录 `actor`（如 `auto:circuit`）、时间戳、
  触发源；通知以 `(kind, date)` 就地替换并保留末 60 条（`_NOTIFY_CAP=60`）。
- **操作留痕**：`data/logs/` 与各类运行日志可回溯；本轮 CI 归因全表已写入工作记忆。

**风险**
- **无用户身份 → 不可归人**：因无鉴权，所有操作都以"系统/自动"名义，
  无法区分"谁导出/谁改了配置/谁触发了熔断恢复"。
- **人工干预不可审计**：双击 `启动服务.bat`、手动改 `secrets.env`、手动放 `.log`
  均为带外操作，不在平台审计范围。

**建议**：若进入多用户场景，必须引入身份（即使只是操作系统的本地账号映射）
  并在关键动作（导出/密钥变更/服务启停）落审计事件。

---

## 6. 可靠性（Reliability）

**现状（正向）**
- 熔断 + "持续空>180s 才升级" 防止错误告警雪崩。
- 翻译退化有 `strip_dangling→is_degenerate` 保原文兜底（`TR.TRV`）。
- 前端降级链 RM→无 THREE/WebGL→fps<26 减半→<20 停帧，且浅色主题换色板，
  保证不同设备都可渲染。

**风险**
- **非确定性结果**：语料实时漂移使同一查询的 cmdb 匹配数/日报数字随时变化，
  复现性差（见完整性节）。
- **测试自身可靠性弱**：负载敏感计时断言、陈旧假设（`available_dates("m1_monitor")[0]==today`）
  产生假失败，削弱"CI 绿=可信"的契约。
- **单点无自愈**：服务挂掉无自动拉起，依赖人工。

**建议**：将 CI 中环境性/计时性断言与功能断言分离，功能断言在隔离环境跑；
关键数据结论附数据版本戳，变"实时漂移"为"可声明快照"。

---

## 7. 交叉结论

1. **强项**：可用性保护（熔断）、真实性溯源字段、降级鲁棒性是亮点；
   本轮修复的火狐可用性事故进一步补强了"前端可用性"。
2. **系统性短板**：**"无鉴权"是根因**——它同时拉低机密性（无访问控制）、
   可问责性（不可归人）、真实性（无来源签名验证的动机不足）。
3. **数据时效性 vs 确定性的张力**：实时抓取带来新鲜度，但以"非确定结果"
   和"CI 假失败"为代价，需用快照/版本戳调和。
4. **运维耦合**：Python 侧改动依赖人工重启、模块停产无告警，是可靠性的主要外部风险。

> 注：以上基于源码静态核查 + 本轮交付验证；动态渗透/模糊测试不在本次范围。
