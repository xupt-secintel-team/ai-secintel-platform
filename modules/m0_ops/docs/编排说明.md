# m0_ops · 事件驱动多智能体编排说明（v2.2 新增）

> 一句话：**新威胁出现时，不用人点，系统自己完成"发现 → 查明影响面 → 产出处置简报"。**
> 本文是 `modules/m0_ops/` 的模块级文档：四个 Agent 怎么分工、状态存哪、怎么复跑演练、有哪些硬约束。

---

## 一、为什么需要它

v2.1 及之前，三个业务模块各自独立：

- `m1_monitor` 按固定节拍采集（RSS 15s / NVD 6h），**采完就放进语料，没人"看"它**；
- `m2_enrich` 的资产/POC 富化**等人来点**（打开详情页或手动调接口）；
- `m3_qa` 等人提问。

一条真实的高危情报从"出现在情报流"到"有人意识到要处置"，中间完全靠人盯。
`m0_ops` 补上的正是这一环：**让模块之间自己协作起来**。

## 二、四个 Agent 的分工

```
live_feed.jsonl ──→ ① PerceptionAgent ──→ ② Orchestrator ──→ ③ EnrichExecutor ──→ ④ BriefAnalyst ──→ ops_briefs.json
   (m1 产出)         感知：发现新事件        编排：优先级/限流      执行：调 m2 富化        研判：产出简报
                     ↘ TraceRecorder（每个 Agent 每一步都留痕）↙
```

| Agent | 职责 | 关键决策 | 失败行为 |
|---|---|---|---|
| ① 感知 PerceptionAgent | 每 `ops_interval_sec`（默认 60s）扫描 `data/live_feed.jsonl` 尾部 400 条 | 触发条件：**KEV 在野利用** 或 **CVSS ≥ 9.0**；与 `ops_state.json` 比对去重，只报新事件 | 扫描异常只记 trace，下轮重试 |
| ② 编排 Orchestrator | 事件分诊与派单 | 排序：**KEV 优先、CVSS 降序**；限流：单轮 ≤ `ops_max_per_cycle`（默认 3）件，防情报洪峰放大负载 | 空队列静默；状态落盘跨重启续传 |
| ③ 富化执行 EnrichExecutor | 对派单事件调 m2 的真实接口 | `GET /api/assets`（受影响版本）+ `GET /api/poc`（缓存档，不触发外网抓取，控制单轮耗时） | 单事件失败不阻塞同轮其他事件 |
| ④ 简报 BriefAnalyst | 产出结构化处置简报 | **双模式**：有 `AISEC_LLM_API_KEY` 走 `/api/chat` 生成自然语言研判；无 Key 用确定性模板（字段拼装，零 token） | LLM 超时/报错自动回退模板 |

旁路的 **TraceRecorder**：每个 Agent 的每一步（谁、何时、对哪个 CVE、做了什么、成败、耗时）都进 trace 环（上限 200 条），`GET /api/ops/trace` 实时可查。

## 三、工程硬约束（与 qa/agent.py 同一套哲学）

1. **模块间零 import**：m0_ops 不 import m1/m2/m3 的任何代码，协作全部通过本机 HTTP 回访（`AISEC_MAIN_SERVER`）与共享数据文件发生 —— 「modules/* → core 单向依赖」的架构约定不破。
2. **失败隔离**：任何一步异常只记入 trace/events，**绝不向主服务抛**；编排线程崩溃不影响采集与问答。
3. **硬限流**：单轮最多 3 个事件；简报留存上限 100 条、trace 上限 200 条，均为环形覆盖，不会无限胀盘。
4. **幂等去重（双防线）**：① `data/ops_state.json` 记录已处理事件 ID，重启后不重复处置；② 落简报前再查一次 `ops_briefs.json` —— 同一 `data/` 目录被第二个实例共享时（例如另起端口的 `--no-live` 自测实例），两边内存态各自独立、可能同时把同一事件当"新"，第二道防线保证**同一事件在全系统只出一份简报**（此缺陷在实弹演练中真实暴露并已修复，单测第 6 组守护）。
5. **无 Key 可用**：全链路默认模板模式，LLM 只是增强不是依赖。

## 四、实弹演练（已做，可复跑）

**目的**：证明"事件出现 → 简报落地"端到端真实可达，并量化处置时效。

**做法**：
1. 确认服务在跑且 `config.json` 中 `m0_ops: true`；
2. 向 `data/live_feed.jsonl` 追加一条构造的 KEV 事件（使用真实存在于语料的 CVE，保证富化有真数据）；
3. 等待 ≤ 一个扫描周期（60s），轮询 `GET /api/ops/briefs`。

**实测结果**（2026-09-27，两次注入）：
- 注入 CVE-2026-85706（KEV，gitlab）：约 **61s** 被感知并产出简报，简报内含真实受影响版本（18.7.0–<18.11.12 等，来自 `/api/assets`）；
- 注入第二条（KEV，另一 CVE）：同样在一个周期内完成处置。

**复跑命令**：
```bash
py -3 tools/评测时效性.py --base http://127.0.0.1:<端口>   # 含编排处置时效测量
curl http://127.0.0.1:<端口>/api/ops/trace                    # 查看编排留痕
```

## 五、接口一览

| 接口 | 说明 |
|---|---|
| `GET /api/ops/status` | 编排器状态：启用与否、周期、各 Agent 简况、已处理事件数 |
| `GET /api/ops/events` | 已感知事件列表（`data/ops_events.json`） |
| `GET /api/ops/briefs` | 处置简报列表（`data/ops_briefs.json`） |
| `GET /api/ops/trace` | 最近 200 条编排留痕 |
| `POST /api/ops/scan_now` | 人工触发一次扫描（不等下个周期） |

## 六、状态文件（`data/` 下）

| 文件 | 内容 | 生命周期 |
|---|---|---|
| `ops_state.json` | 已处理事件 ID 集合（去重依据） | 持续累积，可安全删除（删除=全部重报一遍） |
| `ops_events.json` | 感知到的事件流水 | 环形留存 |
| `ops_briefs.json` | 处置简报（上限 100 条） | 环形覆盖 |

## 七、测试与自测

- **离线单元测试**（不联网、不起服务）：`py -3 modules/m0_ops/backend/test_orchestrator.py` —— 13 项，覆盖去重、排序、限流、模板简报、失败隔离、trace 留痕、**跨实例简报幂等**；
- **端到端回归**：`py -3 core/self_test.py <端口>` 中含 `/api/ops/status|trace|briefs` 接口用例；
- **配置开关**：`config.json` 的 `ops_enabled`（总开关）、`ops_interval_sec`（扫描周期）、`ops_max_per_cycle`（单轮上限）。

## 八、已知边界（诚实清单）

- 感知的是**已入库情报流**里的高危项，不是对原始源的独立二次监测（那是 m1 的职责）；
- POC 富化走**缓存档**（不触发外网实时抓取），保证单轮处置时效；完整抓取仍由用户在详情页触发；
- 简报模板模式是**结构化字段拼装**，深度研判文字需 LLM Key；
- 当前触发条件只有两档（KEV / CVSS≥9），未引入资产画像加权（"打到我在用的组件才报警"）—— 路线图上与 ATLAS 资产类目联动。
