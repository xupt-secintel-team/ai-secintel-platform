## CMDB 文件上传：解析提速 + 多文件合并（m2_enrich）

用户反馈：上传 `E:\cmdb\excel\02_软件资源层.xlsx`（25MB，7 个 sheet，81,207 行）解析过慢（旧代码直接 SIGTERM，>120s 跑不完）。

### 根因与修复（asset_scan.py）
1. `_xlsx_text` 原实现：整 sheet XML（最大 129MB）读入内存 + 非贪婪正则抽行（实测 11.6s，峰值内存数百 MB）。
   - 先试 ET.iterparse：更慢（14.8s，1300 万元素逐个触发 Python 回调）——已否决。
   - 最终方案：**字节级 8MB 分块滚动扫描**，只在 `</row>` 边界切块、每行一次正则、自闭合 `<c .../>` 补位保列对齐 → **~3-5s**。
2. 附带修出一个隐藏 bug：CMDB 导出把中文写成数字字符引用（`&#22791;`=备），旧 `_unescape_xml` 只解 5 个命名实体 → **旧版 xlsx 中文一直是乱码**。已补 `&#\d+;` / `&#x..;` 解码（`_NUMREF` + `_numref_sub`），docx 路径同样受益。
3. `extract_assets`：rows 传入时跳过整个 56MB 文本的 `_norm_text`（每行本来就会单独规范化）。

### CMDB file 模式结构化快速路径（cmdb_scan.py）
- 新增 `_tsv_records`：按表头把 TSV/CSV 行映射成 `{product,version,ip,port,name,owner,env}` 记录 → `_structured_extract`（跳过逐行正则，30 万条 80s→秒级）。
- **多 sheet 表头**：read_upload 把 7 个 sheet 拼成平铺行，每个 sheet 表头不同（软件目录/中间件/数据库/大数据/AI 模型…）。`_row_is_header` 动态检测表头行（首列 `*_id`/id/序号，或 ≥3 个已知列名命中），每个 sheet 独立映射；识别不了的表（数据集/训练作业）自动跳过。
- 语义与 `_SQLITE_TABLE_MAP` 对齐：有 type 列时 product←MW_TYPE/FRAMEWORK，name←MW_NAME；无 type 列时 product←SW_NAME（目录表）。
- 无主机的纯产品记录只保留 CPE 词典能识别的（`_prod_in_dict`），与正则路径语义一致。
- file 分支支持 `files=[{filename,data},...]` 多文件：全部识别成功→合并记录一次分析；任一失败→整体回退 `extract_assets`。行拼接不影响"同行主机关联"。

## CMDB 分析提速（第二轮优化，2026-10-05 上午）

用户反馈「加快 CMDB 分析速度」（提到七八分钟没出结果）。

### 定位到的真正瓶颈（分阶段 profile）
- `scan_assets` 里 `AssetRiskScanner._candidates` 的**宽松回退**：词典没覆盖的产品（本文件 1854 个产品里 1814 个是 nomatch）会对整个倒排索引（28,536 个 canon product）做 `startswith/endswith` **全量线性扫描**——O(产品数 × 索引条目) 的隐藏炸弹。
- xlsx 解析里 `_unescape_xml` 对 129MB sheet 的 215 万个数字实体逐单元格解码（90 万次 re.sub + 360 万次 Python 回调，6.4s）。

### 修复（asset_scan.py）
1. **宽松回退改前缀倒排索引**：新增 `_PREFIX_CACHE` + `_prefix_index()`，对每个 canon product 生成「≥4 字符的所有前缀 + 后缀」两种 key 的倒排索引（45.6 万条，建索引 0.39s）。查表从 O(28536) 线性扫描 → O(1)。**scan_assets 3.91s → 0.09s（43 倍）**。
   - 踩坑：`pfx.setdefault(key, lst)` 用共享引用导致不同 pk 前缀碰撞时丢文档（漏配 25 个 key）。改 `setdefault(key, []).extend(lst)` 后与旧逻辑 mismatch=0。
2. **匹配结果缓存**：`_MATCH_CACHE`（进程级 FIFO，上限 8192），键 `(engine_id, name, version)`，重复产品名直接复用 match 结果。
3. **实体解码提速**：`_unescape_xml` 从「正则回调逐字 chr」改为 `html.unescape`（C 实现）；`_xlsx_sheet_rows` 从「8MB 分块 + 逐行/逐块 sub」改为「整块读入 + 一次性 re.sub 解码」。修正 `_XLSX_NUMREF` 正则分组 bug（`&#x?..;` 单组误当十六进制，导致中文变 `𢞑` 乱码）——改为 `&#x([0-9a-fA-F]+);|&#(\d+);` 双组区分 hex/dec。

### 结果
- 25MB 真实文件 HTTP 端到端：冷启动 7.2s / 热启动 5.4s（原 10.1s），结果 203 CVE / 32 crit / 106 high / 2 KEV 完全一致。
- `tools/_test_asset_scan.py` 52/52 回归通过；多文件合并 + 兜底路径正常。
- 服务已重启加载新代码（8848，旧 PID 20752 已杀）。

### 剩余可优化点（未做，收益递减）
- xlsx 解析 4.5s 里实体解码 ~2.8s 是 215 万个 `&#NNNNN;` 的 Python 逐实体回调硬成本，除非改用 C 扩展否则难再降。
- `_tsv_records` 的 `_split_table_rows` 会一次性 split 全部 8.1 万行（1-3s 波动），可改惰性生成器。

## CMDB 10 文件大批量提速（第三轮，2026-10-05 上午）

用户上传 10 个文件共 335MB（解压 XML 2.8GB），「七八分钟没分析出来」。单文件正常、多文件慢。

### 根因
1. **拓扑/字典/工单类 sheet 占 2.8GB 里的 ~1.7GB**（06_关系拓扑×4=950MB、05 的变更/告警/事件/日志/审计=790MB、00/04 全部）——没有产品/版本/资产 IP 字段，对漏洞分析零贡献但被完整解析；

3. 老 bug：服务器/虚机表的 HOSTNAME 列被当产品名（20 万假产品撞 MAX_PRODUCTS=10 万上限）；OPERATOR_IP 被当资产 IP。

### 修复
1. **sheet 预览跳过**（asset_scan.py）：`read_upload(fname, data, sheet_filter=)`，xlsx 每个 sheet 先用独立流读 64KB 预览前 3 行，`_cmdb_sheet_filter` 判不出资产表头就整表跳过。2.8GB → 640MB。
   - ★ 踩坑：peek 必须用**独立重新打开的流**（`zf.open(sn)` 再开一个），在原 fp 上 read 会把表头行吃掉 → _tsv_records 拿数据行当表头 → mapping=None → 全部记录丢失 → 误入正则兜底（02 变 296 CVE 假结果）。

2. **二进制直传协议**（api.py + panel.js）：`Content-Type: application/octet-stream` + `X-Cmdb-Manifest` 头（URI 编码 JSON 清单），body=文件原始字节顺序拼接；前端 `new Blob(pickedFiles)` 惰性引用零拷贝。旧 JSON/b64 协议完全兼容保留（已验证）。
3. **逐文件流式流水线**（cmdb_scan.py `_CmdbAcc` 累加器）：每文件独立「解析→表头映射→结构化/正则抽取」用完即弃，父流程按文件顺序合并（adv 行号偏移防跨文件同行关联串位）；单文件解析失败不再拖垮整批（per-file 结构化/正则决策）。内存从「全部行×10 文件」降为「单文件行」。
4. **产品列语义修正**：product 只认「类型列 / 产品名列」，HOSTNAME/实例名不再当产品（29 万假产品→1.7 万真产品）；表头只要有 IP/域名列即视为可识别（服务器/网络设备表保住主机提取）；`DOMAIN_NAME` 加入域名列；OPERATOR_IP 等操作员列排除。
5. **实体解码缓存**：`_XLSX_REF_CACHE` 按整实体字节缓存（215 万实体仅 ~851 种）。
