用户截图反馈。**两类问题浏览器都不报错、只能靠算**：

**这类问题最难查**：CSS 静默失败，DevTools 里也不一定显眼。

### 2. 拿"文字色"当"按钮底色"
我给打包按钮写了 `background:var(--accent-3); color:var(--surface-1)`。两个错：

- `--surface-1` 是**半透明白** `rgba(255,255,255,.024)`，压在任何强调色上 → 1.02，全糊。
正确做法：底色 `--accent` 族 + 文字 `--accent-ink`（#fff）。
项目有 `--accent-ink` 就是专门给强调色底配文字的，我一开始没用它。

`--txt-4` 在两主题 ratio 只有 2.87 / 2.42。**≤11px 的文字一律提到 `--txt-3`**（4.80/4.26）——

## 第四轮：修「实时监测·最新情报」左栏被翻译功能搞坏（用户截图反馈）

### 症状
用户原话「出问题改成原来那样」。截图：标题被挤成**竖排一条**、右侧大片空白、
底部还长出**横向滚动条**。

### 根因不是 slice 长度，是布局
我一开始怀疑 `panel.js` 把 `.slice(0,44)` 放宽到 `.slice(0,120)` —— **猜错了**。
真因：翻译块 `.trl` 是 `TR._run()` 用 `t.el.after(ph)` 插进去的**兄弟节点**，
而 `.lat` 是 `display:flex`（不换行）的行：

| 元素 | 角色 |
|---|---|
| `.latd` 日期 / `.badge` ×2 / `.latc` CVSS | `flex:none` |
| `.latt` 标题 | `flex:1 1 auto; min-width:0` |
| **`.trl` 译文块** | **也成了并列 flex item** ← 抢位元凶 |

只有"翻译开着 + 宿主是 flex 行"才炸。纯看代码很难在提交前发现。

### 修法（保留全页翻译，不删功能）
1. `panel.js`：标题包进 `<span class="latmain">` —— 译文落在这个纵向容器**内部**，

2. `styles.css` 补 `.latmain{flex:1 1 auto;min-width:0;flex-direction:column}`、
   `.latmain .latt{flex:none}`（纵向容器里 `flex:1` 会让它被拉高）。
3. 同类隐患一并修：`.card>h3`（TR.SEL 里的 `#db h3`，会挤掉

4. `.trl` 加通用防溢出：`min-width:0; max-width:100%; overflow-wrap:anywhere`
   ——译文里的长 URL/标识符不得撑宽容器。

`检查对比度.py` 新增「全站变量存在性」段后，立刻报出
`.hopchip{background:var(--bg-3)}` —— **`--bg-3` 项目里根本没定义**
（只有 `--bg` / `--bg-2` / `--elev-1` / `--elev-2`）。
浏览器静默回落到透明 → 跳转路径标签失去底色。已改用 `--elev-1`。

新脚本要排除两类**假阳性**，否则会被噪声淹没：
- `var(--x, 兜底)` 带 fallback（`--i` / `--mx` / `--my`）→ 未定义不影响显示
- JS 内联 `style="--c:..."` 注入的局部变量（`.chip cat` 分类色）→ CSS 里查不到

- `rule()` 只取同名规则的**第一个**匹配块，而 `flex-wrap:wrap` 写在后面的补丁规则里
  → 又一个假失败。改成**合并所有同名规则**（这才是语义上正确的做法）。
- 给译文块角标设 `font-size:9px` 触发 `_test_digest_panel.js` 的「无 9px 字号」断言

### 新增文件
- `tools/_test_translate_layout.js`（24 项）—— 钉死"译文块不得破坏宿主布局"

## 第五轮：在别人机器上测出来的 4 个"本地全绿但交付即炸"的问题

### 触发
用户把包发给别人测，截图报三件事：
① `启动服务.bat` 双击没用，必须在文件夹里开终端敲 `py -3.13 core/server.py 8899`
② `启动服务_守护.bat` 报 `did not find executable at D:/python/python.exe: ????????`
③ 那台机器的 `config.json` 里 `"port"` 存的是**一段中文说明**，不是 8848

### 根因与修法

**1. bat 里写死了本机绝对路径**
`for %%P in ("D:/python/python.exe" "py -3.13" ...)` —— 两条都只在我这成立。
- `D:/python/python.exe` 是我本机的，别人没这个目录；
- `py -3.13` 别人装的可能不是 3.13。
★ **关键**：`for %%P in` **不会跳过不存在的可执行文件**，
  拿一个别人机器上没有的路径去试就报 `did not find executable at ...`。
  改用 `for %%I in`（**会跳过**），候选只留到处都有的
  `.venv` / `py -3` / `python` / `python3`。

**2. `.venv` 存在 ≠ 能用**
别人机器的 `.venv` 多半是整个拷过来的，`pyvenv.cfg` 里记的是**原机器的解释器绝对路径**。
`if exist` 会通过，真执行立刻失败。
→ 选定后加一道 `%PYEXE% -c "print(1)"` 启动自检，判据是**能不能跑**不是文件在不在，
  失败时直接告诉他"删掉 .venv 重跑安装.bat"。

**3. 依赖探测用 import，拖慢启动**
原脚本为了打印"选了谁、缺什么"**连续起 5 次解释器**，其中 `import torch` 实测 **6.6 秒**。
→ 合并成一次调用 `tools/探测解释器.py`，且用 `importlib.util.find_spec` 查元数据
  （**约 0.1 秒**）而不是真 import（2.7 秒起）。判据上"装没装"就够 ——
  真导不动时 server.py 启动会抛 ImportError，比提前花几秒探测更明确。
实测：探测段 2.67s → 0.64s。

**4. config.json 被填成文字 → 服务一行日志都来不及打就崩**
`"port": "控制台端口，但可启动时用命令行覆盖：py -3.13 core/server.py 8899"`
→ 原先 `int(config.get("port") or 8848)` 直接 `ValueError`。
→ 新增 `_coerce_port()` / `_cfg_num()`：非法值回落默认并**明确告诉用户改哪里**。
  同类暴露面还有 `fast_interval` / `auto_refresh_hours` / `auto_refresh_sec`，一并保护。
实测：注入坏配置后服务照常起来（索引 8.1s，模块全装载）。

### 批处理编码（另一个隐形杀手）
截图2 满屏 `'t' is not recognized as an internal or external command`。
**10 个 bat 全部无 UTF-8 BOM**，共 209 行中文注释。
`chcp 65001` 只改**显示**代码页，**不改 cmd 解析批处理用的编码**（仍按 GBK），
中文 3 字节被 GBK 按 2 字节切 → 碎片里的 `&` `|` 被当命令连接符
→ **每一行中文注释都执行一次**，64 行 = 64 次报错 + 64 次进程创建。
这就是"启动时间过长"的另一半原因。
→ `tools/_fix_bat_encoding.py` 统一补 BOM + CRLF（只动编码，不碰逻辑）。

### 交付可移植性检查（新增 tools/_test_portability.py，61 项）
**这类问题本地全绿也抓不到** —— 只有一个判据："放到别人机器上还成立吗"。
- bat 可执行行不得含盘符绝对路径（**注释里不算**，那里是修复记录，要保留）
- 解释器候选必须用 `for %%I` 且不含 `py -3.13` 这类小版本
- 选完必须验"能不能真跑"
- 探测不许用 import
- 所有 bat 必须有 BOM + CRLF
- config 数值字段填文字要能回落
★ 写这个测试时踩了两处自身误报：把注释里的历史路径当成现行错误、
  把 bootstrap 段 `for %%P in ("py -3"...)`（存字符串，%%P 正确）当成漏网。

### 自身另一个坑
`python core/server.py &` 在本环境**会被会话回收**，进程悄悄消失、
日志停在"装载模块"就断了 —— 看起来像启动失败，其实是被回收，
排查方向完全跑偏。→ 改用 `tools/_smoke_boot.py`：**前台阻塞 + 定时打接口 + 主动关闭**，
才能拿到可信结论。

## 第六轮：用户报「启动时间过长」—— 真凶是启动线程被网络探测堵死

### 症状
双击 `启动服务.bat` 后 **100 秒端口都没绑上**。此前一直以为是"慢"。

### 定位：faulthandler dump 线程栈（一步到位）
```python
faulthandler.dump_traceback_later(45, exit=True)
```
抓到主线程栈：
```
modules/m1_monitor/api.py:836  start()        ← 启动钩子，主线程同步
  live.py:348  blog_feeds()
    core/net.py:145  detect_proxy()           ← 卡在这
```
后台线程（live / m0 编排）**都正常跑着**，但主线程被堵 →
走不到 `ThreadingHTTPServer(("127.0.0.1", port))` → **端口永远不绑定**。
用户访问的是端口，所以表现为"打不开"，而不是"慢一点"。

### 根因：开销是**累积**的
`detect_proxy()` 四段：
| 段 | 单段耗时 |
|---|---|
| 环境变量 | 2 URL × 4s = 8s |
| 上次代理 | 2 URL × 4s = 8s（本机无代理，白等） |
| 直连 | 2 URL × 4s = 8s（同上） |
| 扫监听端口 | **本机 46 个** × 2 URL ÷ 8 线程 ≈ 46s |

`PROBE_URLS[0]` 是 `google.com/generate_204` —— **境内必然超时**，
所以每段都是满额等完，不会"快速失败"。实测 `detect_proxy(force=True)` = **19 秒**。

### 修法（两道都做）
1. **`modules/m1_monitor/api.py`**：源探测挪到 daemon 线程（`name="fastlane"`），
   主线程立刻返回。即使探测慢，也只慢在后台。
2. **`core/net.py`**：加总预算 `DETECT_BUDGET`（默认 8s，`AISEC_PROXY_BUDGET` 可覆盖），
   四段**共用一个 deadline**，每次 curl 的 `--max-time` 按剩余预算压低。

实测：
| 指标 | 修前 | 修后 |
|---|---|---|
| `detect_proxy` | 19.0s | **8.2s**（稳定卡在预算内） |
| 端口就绪 | >100s（没绑上） | **23.7s** |

### 踩过的坑（都写进测试了）
- **预算只能在函数入口算一次**。我最初只加在"扫端口"段，实测仍 19s ——
  因为**前面三段各 8s 早就把预算花光了**。只盯最显眼的那段会漏掉真正的大头。
- **`ThreadPoolExecutor.map` 是惰性的**，等第一个结果返回就可能已经超支 8 秒。
  预算必须用 `submit(fn, arg, deadline)` **传进每个任务**，
  在消费结果处比对 deadline 是来不及的。
- 写测试时两次**自己把自己判成 FAIL**：注释里写的 `blog_feeds()` 字样、
  `%%` 转义。前者要先剥注释再查；后者要用正则的 `{2}` 量词表达 bat 的双百分号。

### 顺手做的
- 左侧「实时监测 · 最新情报」按用户要求**不再翻译**（`TR.SEL` 去掉
  `#latestbody .latt`）。侧栏太窄，译文块会把每条撑成两行、9 条占满整屏；
  且条目本就是"扫一眼"的，点开详情里全翻。
  `.latmain` 那层壳**保留** —— 万一以后加回来，译文块落进纵向容器挤不坏布局。
- 新增 `tools/_test_startup_block.py`（20 项，**含实测计时**），挂 CI 第 8 步。
- CI 从 5 步扩到 **8 步**：+ 可移植性 + 批处理编码 + 启动阻塞。

## 第七轮：bat 双击还是起不来 —— 之前"补 UTF-8 BOM"的方案被实测证伪

### 触发
用户连续 5 次报「启动不了检查」。命令行 `python core/server.py` 正常（22.2s），
但 `cmd /c 启动服务.bat` 60 秒超时。

### ★ 关键证伪：UTF-8 BOM 根本没用（这是本轮最大教训）
我一直以为"加 UTF-8 BOM 就能让 cmd 按 UTF-8 解析"，**实测证明是错的**。

对照实验（同一段中文注释，两种编码各跑一遍）：
```
GBK 无 BOM  → 输出 GBK_OK，干净无报错        ✅
UTF-8 BOM   → '锘緻echo' 不是内部或外部命令   ❌
```
`EF BB BF`（BOM）被 GBK 显示成 `锘緻`，且与 `@echo off` 连成一条命令被执行。
**结论：cmd 解析批处理文件永远按系统 ANSI（简体中文 = GBK/CP936），根本不看 BOM。**
BOM 不但没用，反而成了命令前缀的一部分。

### 正确修法（三件事）
1. **10 个 bat 全部从 UTF-8 BOM 改成 GBK 无 BOM**（中文注释用 GBK 字节写，
   cmd 按 GBK 解析正好一一对应，不再产生半个汉字 → 不再有伪命令）。
2. **删掉所有 `chcp 65001`** —— 它只改**显示**代码页，改不了解析编码，
   而且文件变 GBK 后它反而让显示乱码、制造假象。
3. **修一个真 bug**：`启动服务.bat` 里 `echo [!]   A) 删掉...` 的 `A)` 右括号
   没转义，在 `if errorlevel 1 (...)` 块内被 cmd 当闭合括号 →
   报「此时不应有 删掉本项目目录下的。」→ 转义成 `A^)` / `B^)`。

### 连带改动
- `tools/_fix_bat_encoding.py`：从"补 UTF-8 BOM"重写为"转 GBK 无 BOM"，
  `--check` 判据从「有 BOM」改成「无 BOM + 能 GBK 解码 + CRLF」。
- `tools/_test_portability.py`：编码段断言同步翻转；`bat()` 读取改用 `gbk` 解码
  （原来 `utf-8-sig` 读 GBK 文件直接 UnicodeDecodeError）。
- `运行CI.bat` 第 7 步文案从「缺 BOM」改成「应 GBK 无 BOM」；
  第 7 步原注释里的 `✓`(U+2713) GBK 装不下，改成 `[OK]`。

### 实测结果
| 项 | 结果 |
|---|---|
| `启动服务.bat --setup` | 退出码 0，2.8s，无任何乱码/伪命令报错 ✅ |
| 完整冷启动 | 端口 21.5s 就绪，/api/health 200 serving ✅ |
| `_test_portability.py` | 71 项全过 |
| `_test_startup_block.py` | 20 项全过 |
| 前端 11 个 JS 测试 | 全过 |
| `组装前端.py --check` / 对比度 / static | 全过 |

### ★ 教训（钉死）
**cmd 解析 bat 永远按 GBK，不看 BOM。** 给 bat 加 UTF-8 BOM 是错的方向，
BOM 字节反而会被当命令前缀（`锘緻echo off`）。正确做法是 bat 存 GBK 无 BOM。
另外：`if (...)` 块内 echo 文本里的裸 `)`（如 `A)` `B)`）必须转义成 `^)`，
否则 cmd 提前闭合括号。`set "VAR=含(括号)"` 用引号包裹是安全的，不算。

## 第八轮：翻译输出整段 "a, a, a, e, e, e" —— 模型重复退化 + 截断残句诱因

### 症状（用户截图）
CVE-2026-102173 卡片的标题译文退化成：
`柯基 - 自由页面构建器...很容易被存储跨线脚本, a, a, a, a, a, a, a, e, e, e, ...`
详情块的译文却基本正常。规律：**标题是前端截断显示的残句**（结尾悬在
`up to, a...`），详情是完整句子。

### 三层根因
1. `model.generate()` **完全没设防重复退化的参数**（no_repeat_ngram_size /
   repetition_penalty 都没给），Marian 小模型在残句输入上偶发解码循环；
2. 截断标题的**悬空尾巴**（", a..."）是循环的强诱因 —— 解码器从半个词上续写；
3. 输出没有兜底检测，退化文本原样给用户（比不翻还糟）。

### 修法（translator.py，三层防御）
1. **输入层** `strip_dangling()`：剥掉结尾的悬空尾巴（有省略号剥 1~2 字母；
   无省略号只剥单个小写字母，`, IP`、`, 6.3.1` 这类正常结尾不动）。
2. **生成层**：`generate()` 加 `no_repeat_ngram_size=3`（AISEC_MT_NO_REPEAT 可调，
   对中文安全——正常中文几乎无重复 3-gram）+ `repetition_penalty=1.2`
   （AISEC_MT_REP_PEN），坏值经 `_env_num()` 回落默认。
3. **输出层** `is_degenerate()` 纯函数检测（三判据：同一短 token ≤3 字符
   连续 ≥5 次；token ≥20 且 ≤2 字符占比 >50%；单字符连续 ≥15 次）。
   命中 → 用更强参数重试一次 → 仍退化 → **该块保原文**（翻错不如不翻）。

### 顺带挖出的真 bug：术语表英文源词只认空格
`cross site scripting` 匹配不了实际文本的 `Cross-Site Scripting`（连字符写法
才是漏洞标题的主流）——**整条校准一直在失效**。修：构造正则时把
`re.escape()` 产生的 `\ ` 替换成 `[\s\-]+`。全部 38 条词表受益
（use-after-free、zero-day 等连字符变体从此都能命中）。
另补 `("kirki", "Kirki", ("柯基","Kiki","基基"))`（产品名被翻成犬种名）。

### 测试（_test_translator.py 44 → 73 项）
- strip_dangling 7 断言（含 `, and including` / `, 6.3.1` / `, IP` 不误伤）
- is_degenerate 6 断言（截图乱码必须命中；正常中英长句不误伤）
- _gen 兜底用假模型验证两条路径：重试修好 / 重试仍退化保原文；
  静态断言钉死 generate 必须带反重复参数、strip_dangling 在切块前
- 词表连字符变体、_env_num 坏值回落
- ★ 假模型分叉要用 decode 按 strict/always 模式返回不同文本，
  第一次写成了 generate 里选返回值，decode 静态方法感知不到，白跑两轮

### 真实模型实测（截图同款输入）
修复前：`...存储跨线脚本, a, a, a, a, a, a, a, e, e, e...`
修复后：`Kiki - Freform Page 构建器、WordPress网站创建器和自定义插件都容易
通过所有版本的注册元数据被存储跨站脚本`（无退化、尾巴剥掉、跨站脚本校准生效；
复测一次 Kirki 正确保留）

### 教训
**小模型翻译的退化不是"质量差"而是"事故"，必须输出侧兜底。** 输入侧清理
（去悬空尾巴）+ 生成侧参数 + 输出侧检测三层都做，缺一层都会再翻车。

## 第九轮：① 问答区 UI 放大加粗 ② 每日报告只显示四大类

## 第十轮：问答 API 调用报错 max_retries —— 参数位置放错了

### 症状（用户两张截图）
① 顶部横幅：`大模型调用失败，已降级为检索模板：Completions.create() got an
unexpected keyword argument 'max_retries'`；
② 状态条显示"未配置模型"——但用户明明在「模型设置」里保存了 DeepSeek Key。

### 根因一（真 bug）：max_retries 传错了地方
openai 3.x 里 `max_retries` 是 **`OpenAI()` 构造函数**的参数，传给
`chat.completions.create()` 直接 TypeError。generator.py / multi_hop.py /
agent.py 三处全传错了。之前没暴露是因为用户一直没配 Key（走模板模式没真调）。
venv python 一行验证复现报错（与截图一字不差），并确认
`OpenAI.__init__` 有 `max_retries`、`create()` 没有（`timeout` 两处都合法）。
修法：三处的 `max_retries=...` 全部挪进 `OpenAI(base_url=..., api_key=...,
max_retries=...)` 构造。

### 根因二（误导性提示）：状态条只看服务端 env_key
`probeServer()` 里 `env_key` 为空就显示"未配置模型"，**完全没看浏览器端
localStorage 里保存的配置** → 已存 Key 的用户被误导成"配置丢了"。
修法：else 分支先看 `cfg()`，浏览器端有 api_key+model 就显示
"已用本机浏览器配置（xxx）；服务端未设 AISEC_LLM_API_KEY，此处配置优先"。

### 防回归（_test_acceptance_hardening.py 54 → 60 项）
新增 ⑦ 段 6 条断言：三个文件的 `create(...)` 块里不得出现 `max_retries`；
它要么出现在 `OpenAI(...)` 构造里、要么整个文件不用。正则要容忍嵌套括号
（`(?:[^()]|\([^()]*\))*`）。

### 教训
**SDK 参数位置要用 `inspect.signature` 验，不能靠记忆。** openai 1.x→3.x
的参数表变过；写调用前一行 `inspect.signature` 就能省一次线上报错。
另外"未配置"类提示必须把**所有配置来源**（环境变量 + 浏览器端存储）都查完
再下结论，只查一处必然误导。

## 第十五轮 · 译文"左边不正常右边正常"= 缓存版本问题（2026-10-07）

用户截图：同一屏里左侧检索卡片的 `.snip` 译文仍是 `…跨线脚本, a, a, a, a, e, e, e…`，
右侧检查器的 `.desc-p` 译文完整正确。两块走**同一个后端接口**、同一页面同一次操作。

### 根因：不是模型，是 localStorage 译文缓存
- 缓存 key 以前只有 `hash(原文)`，**不含"由哪个版本的翻译管线产出"**。
- 左侧那条是**旧代码时期**翻好并缓存的；后端第十四轮修好退化后，
  它依旧命中缓存、原样显示。右侧是刚翻的（新代码）所以正常。
- → **光修后端永远修不掉用户看到的"一半好一半坏"。**
- 排查手法：把截图左右两半各裁出来放大，逐字比对两条译文的差异；
  再 `grep hash(` 看 key 构成 —— 一眼看出没有版本维度。

### 三层修法（`frontend/app.js`）
1. `TRV: 'v2'` 版本盐掺进 `hash()`；`asi-trv` 存 localStorage，
   启动时不一致 → **整库作废重翻**（避免半新半旧混一屏）。
   ★ 以后改 `translator.py` 的翻译行为，**必须把 TRV 加一**。
2. `isBadDst()` —— 后端 `is_degenerate` 的**前端镜像**（同样 4 条判据，
   同样"判据②只按 `[-·・—]` 切、不含空白"以豁免 "very very very"）。
   加载缓存时逐条过滤 → 命中即 `delete`（不是只跳过）+ 回写。
3. `translate()` 写缓存前也拦截：坏结果**宁可不显示**、下轮再试，不许进缓存。

### 测试
新建 `tools/_test_translate_cache.js` **24 项**（CI 的 `for %%f in (tools\_test_*.js)`
会自动收，无需改 bat）。★ 关键：**把 `isBadDst` 抠出来用 `new Function` 真跑**
——静态断言只能证明"代码写了什么"，证明不了"判据算出来对不对"。
用例直接拿用户截图里的两条原文当 fixture（左：判退化；右：保留）。
全量：JS 全绿、PY 全绿、组装一致、compileall、对比度 9、bat 编码 10、启动阻塞 20。

### 教训
- **"修了后端"和"用户看到修好了"是两件事**：任何带本地缓存的计算结果，
  改算法/模型时必须**同步失效缓存**（版本盐是成本最低的做法）。
- 前端 `hash()` 这类"纯函数"很容易被当成永远正确，其实它编码了
  **隐含的算法假设**；算法变了，key 的语义也就变了。
- 用户描述"左边不正常右边正常"时，第一反应不该是布局 —— 同一组件
  不同列表现不同，优先怀疑**数据来源不同**（缓存 vs 实时）。

## 第十六轮 · 「下载」按钮变成「跳转预览」（2026-10-07）

用户截图：点「⬇ 下载七章制 Markdown」→ 浏览器**跳到**
`127.0.0.1:8848/api/cmdb_scan?id=CMDB-...&md=1`，显示一整页 Markdown 源码，文件没落盘。

### 双重根因（前后端各一半，缺一边都不会发作得这么明显）
1. **后端**：`req.send(...)` 只有传 `filename=` 才写
   `Content-Disposition: attachment`（`core/server.py:_send`）。
   `?md=1` 的导出分支只设了 `ctype="text/markdown"`、**漏了 filename**
   → 浏览器按 text/markdown **内联渲染**。
   `/api/cmdb_scan/tickets` 一直是对的（它传了 filename），**所以只有 md 入口坏** ——
   典型"同一模块里有的接口对有的错"，肉眼很难发现。
2. **前端**：`downloadFullMd()` 只写 `a.href` + `target=_blank`，**没设 download**，
   把"下不下载"完全押在服务端响应头上了。
   ★ 通用规律：**`<a href>` 触发的是"导航"不是"下载"**，
   只有 `a.download` 或服务端 `Content-Disposition: attachment` 才是下载。少一个用户就离页。

### 修法
- 后端加两个辅助：`_md_filename(kind, rep)` + `_md_response(req, md, kind, rep)`，
  **所有 md 导出走单一出口**。修的过程中被自己的测试逮出**还有 2 处**同类漏洞
  （`/api/remediation?md=1`、`/api/stix?md=1`）—— 一开始只看到用户报的那一个。
- 前端 `downloadFullMd` 改 `fetch` + `blob` + 复用 `downloadBlob`
  （**不再依赖服务端响应头**）；顺带能读出后端 JSON 里的 error 文案
  （原来 `a.href` 开新标签，出错只在新标签显示一段 JSON，用户看不懂）。

### 测试
- `tools/_test_md_download.py`（13 项）：**真起服务打接口**，断言响应头里
  确实有 `attachment` + `.md` + RFC 5987 中文名。不真打接口抓不到 ——
  源码层面"设了 ctype"看着完全正常。没样本时优雅 SKIP 并回落到静态兜底。
- `tools/_test_md_download_panel.js`（20 项）：前端走 fetch+blob+downloadBlob；
  并**逐行扫描** api.py 确认没有裸调 `req.send(ctype="text/markdown")` 的残留。

### 教训
- **测试正则跨函数边界会误报**：初版 `/req\.send\([^;]*?text\/markdown/g`
  从某处 req.send 一路吃到几十行外另一个 text/markdown，**误报 3 条**。
  改成逐行 + 向前回溯 3 行，并**豁免被检查的那个函数自身**。
- **断言要落在"真正做那件事的函数"上**：`a.download` 在 `downloadBlob` 里设，
  断言写在 `downloadFullMd` 上 → 把好代码判成坏的（踩了两次）。
- 用户报"点了没反应/不对"时，先问**是不是发生了导航**（看地址栏变没变）——
  导航和下载在用户视角都是"屏幕变了"，但根因完全不同。
- **同一模块里修了一处，要扫全模块找同类**：用户只报了 1 个 md 入口，
  实际有 3 个；靠测试的"全局扫描"断言才全揪出来。

### 第 5 轮查出并修复的 3 个真实缺陷

**R5-A `_VERSION_RE` 覆盖不全（版本影响面）**
- 症状：`CVE-2026-7482 影响范围` 有数据却不渲染版本段。
- 根因：`deep_answer._VERSION_RE` 只有 `哪些版本|影响.*版本|…`，**"影响范围"匹配不上**；
  而 `content_answer._FIX_Q` 里明确有 `影响范围` —— 同一能力两处判据不一致。
- 实测证据：`/api/assets?id=CVE-2026-7482` 明明返回 `affected_versions:["<0.17.1"]`。
- 修：补全 `影响范围|影响面|影响哪些|受影响(组件|资产|版本)|哪些组件…`。
- 加强：`version_section` 改为**依次尝试问题里的 CVE + 证据池所有 CVE**（原先只试第一条，
  产品名提问且 docs[0] 非资产类时静默返回 None）。

**R5-B 没有"修复建议"专属段落**
- 症状：`CVE-2026-7482 的修复建议` 只回通用情报汇总，答不出"升级到哪版"。
- 实测证据：`/api/detail?id=CVE-2026-7482` 的 `patch_links` 有 3 条（含
  `releases/tag/v0.17.1`）、`cpe` 带 `end_excl: 0.17.1` —— **数据够，只是没渲染通道**。
- 修：新增 `fix_section()`，从补丁链接抽版本号（`_ver_from_links`）+ CPE 版本区间，
  产出"升级到 vX / 受影响区间 / 补丁 / 厂商公告"，全部带依据；抽不到如实说明。
  注册进 `deep_sections`（顺序：极值→统计→攻击链→**修复建议**→版本→论文）。

**R5-C 核心检索式污染 = 串扰根因（最隐蔽）**
- 症状：`CVE-2025-15063 的攻击链是什么` 结论第 1 条写的是
  **`CVE-2025-68664`（LangChain 反序列化）**，与本 CVE 完全无关。
- 根因：`multi_hop._core_query` 把它改写成 `'CVE-2025-15063 攻击链 什么'` ——
  **"攻击链"这个询问角度词进了检索式**，BM25 把标题含"攻击链"的博客顶到首位，
  而那篇讲的是别的 CVE；"什么"也因 `_ASK_RE` 没有 `是什么` 而残留。
- 修：`_ASK_RE` 补 `是什么|啥|…` + **把所有"询问角度词"（攻击链/修复建议/影响范围/
  影响面/受影响版本/攻击手法…）从检索式剔除**（它们由 deep_answer 对应段落负责）；
  `_RESIDUE_RE` 补 `影响|版本|组件|资产|范围|哪些|怎么|处置|修复|方法|措施|方案`。
- 效果：`CVE-2025-15063 的攻击链` 证据从 8 条（串到 CVE-2025-68664）**降为 1 条**（只有自己）。

### ★ 本轮踩到的两个"自伤"教训（已写进代码注释与测试）

1. **尾管道 = 空分支，`re.sub` 会给每个字符插空格**。`_ASK_RE` 末尾多一个 `|`，
   导致 `Ollama 漏洞` → `' O l l a m a   漏 洞 '`。症状极怪（CJK 逐字空格），
   但根因就一个字符。**写交替正则务必检查没有 `|` 结尾或 `||`**（测试已加断言）。
2. **探针本身会有 bug，判据也会过严**：
   - 攻击链探针 `has_steps` 用 `1\.\s`，把 `1. **标题**` 这种**列表编号**误判成步骤
     （真判据应看 `## 攻击链` 段落 + `attack_section`）。
   - 我第一版 e2e 断言"结论里不得出现别的 CVE"——**过严**：一篇讲 Ollama 整体的
     博客会正当列出同族 CVE（`CVE-2026-7482 内存越界、CVE-2024-37032 路径遍历…`），
     且把被问 CVE 当主角。正确判据是"evidence[0] 就是被问的 CVE + 主角要点含它"。

### 并发口径（查清，非缺陷）
- 现象：探针测 6 并发 7.9~9.3s，单发仅 0.1~4.4s，疑似锁竞争。
- 实测：**热缓存下 6 并发 wall=1.42s，每请求 1.1~1.4s（近线性）**；
  慢是因为 6 个查询**全冷**，纯 Python BM25 over 118k 文档受 **GIL** 串行 ≈9s。
- 已核实 `embedder.encode` 无锁且快（6 并发 0.16s），不是它；`MT_LOCK`/`VEC_LOCK`
  只管建库/翻译下载，不在问答路径。**这是 GIL 固有行为，不修**，
  在 `_test_qa_round5.py` 固化成"热并发 wall < 串行和"，不断言绝对毫秒（机器无关）。

- 改：`qa/deep_answer.py`（_VERSION_RE / fix_section / version_section）、
  `qa/multi_hop.py`（_ASK_RE / _RESIDUE_RE）。

## 情报问答模块 · 7 轮独立实测审计（第 6 轮完成）

第 6 轮**换角度**：从「知识库本身」出发审问答（前 5 轮都是从"某个问句"出发）。

### R6-A（真缺陷，最严重）诚实边界不一致 —— 假实体被"凑数"
- 症状：同一系统 6 个"不存在"的查询里，**只有 3 个如实说"没有"**：
    `foobarbaz-9x 的安全漏洞` → ev=8（凑满）
    `ZzzNonexistentProduct 有哪些漏洞` → ev=4
    `CWE-99999 相关的漏洞` → ev=8
  而 `CVE-2099-99999` / `假来源` / `中文随机` → 正确 no_relevant。
- 根因（两层）：
  1. `strong_terms()` 把**任意拉丁词**都当"铁证"（`foobarbaz-9x`、`cwe-99999` 都进 strong）；
  2. **致命**：`is_relevant` 的分支 ②③ 只判 `strong` **非空**、不判**是否命中**：
     ```
     if vs >= VECTOR_FLOOR and strong: return True      # ②
     if doc["_fusion"]=="bm25+vector" and strong: return True  # ③
     ```
     `foobarbaz-9x` 从未出现在任何文档里，却因 `strong` 非空放行了
     语义路 0.9008~0.9054 的噪声 → 假查询拿到 8 条无关情报。
     **把"提问里有标识符"当成了"标识符在库里"，两件事完全不同。**
- 修：②③ 改为要求 `strong_hit`（标识符**真的出现在文档文本里**）。
- 效果：诚实率 **3/6 → 6/6**；真 CVE（CVE-2014-0160/2021-44228）不误杀，
  且证据更聚焦（CVE-2014-0160 从 8 条 → 2 条）。

### 三个"看着像 bug、实为误报/设计"（已澄清，不修）
- **R6-B `vector_probe` hits=0** —— **探针自身 bug**：中文 q 未 URL 编码，
  请求失败返回 `{}`。产品侧完全正常（count=118388，hits 余弦 0.91）。
  ★ 教训：**探针也会有 bug**，报"接口坏了"之前先 `urlencode` 中文。
- **R6-C `corpus.total=106844` vs `vector_count=118388`** —— 差 11544 是
  **同一文档分多块**（chunk），合理。测试固化为"vector ≥ corpus 且 corpus==stats"。
- **R6-D `/api/corpus` 无 `sources` 字段** —— 该接口**有意精简**（轻量清单，
  7 个字段）。但确实导致"知识库概览看不到来源分布" —— 属**模块 1/2 的
